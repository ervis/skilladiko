# Repo Workflow

## Purpose

Use this skill when carrying out substantial repository work and you need to keep implementation, canonical documentation, task history, reusable lessons, and commit hygiene aligned.

This skill defines a general workflow for completing work end-to-end in a way that preserves durable project knowledge.

## Core Principles

- Treat the repository’s canonical documentation location—typically `docs/`—as the version-controlled record of the system.
- Canonical documentation should be commit-accurate: at any commit, it should describe the system as it exists at that commit.
- Documentation updates are part of task completion, not optional follow-up work.
- Preserve meaningful implementation history when it would otherwise be lost.
- Preserve reusable lessons when they should improve future work.
- Keep documentation high-signal, concise, and practical.

## When to Use This Skill

Use this skill when the task is substantial, especially if it:
- changes behavior
- changes architecture or design
- affects invariants, usage, or operations
- updates canonical documentation
- spans multiple files
- requires preserving meaningful reasoning or implementation history
- reveals reusable lessons for future work

This skill is designed to compose with more specialized skills such as:
- `research-codebase`
- `create-plan`
- `implement-plan`
- `commit`

## Default Workflow

### 1. Understand the task
Before coding:
- identify what the task actually requires
- make assumptions explicit
- if something is ambiguous, state the ambiguity and the most likely interpretation
- inspect repository context before making changes

### 2. Plan when needed
If the task is ambiguous, multi-step, or substantial:
- create a short plan before implementation
- identify expected file changes
- identify expected documentation impact
- identify whether the task likely needs a task log or retrospective

Use `create-plan` when a more explicit plan is helpful.

### 3. Implement the change
Make the required code, configuration, documentation, or template changes.

Keep changes:
- consistent with existing repository conventions
- precise and minimally noisy
- aligned with the actual task rather than speculative improvements

Use `implement-plan` when executing from an approved or explicit plan.

### 4. Update canonical docs
If the task changes durable system truth, update the relevant canonical documentation in the same change.

Durable system truth includes things like:
- architecture
- behavior
- invariants
- usage
- operations
- important design rationale

Do not leave canonical documentation stale when the code or workflow has changed.

### 5. Preserve task history when needed
For substantial tasks, create or update a structured task log if the repository uses task logs.

A repository may keep task logs in a location such as `docs/task-logs/`.

Task logs should capture meaningful execution history, such as:
- important human clarifications
- the initial plan
- discoveries
- changes in direction
- key implementation decisions and reasons
- validations performed
- documentation updates made

Do not commit raw transcripts or low-signal step-by-step chatter.

### 6. Preserve reusable lessons when needed
If the task reveals meaningful reusable lessons, create or update a retrospective if the repository uses retrospectives.

A repository may keep retrospectives in a location such as `docs/retrospectives/`.

Use retrospectives for lessons about:
- planning
- execution
- prompting
- workflow
- documentation
- agent behavior
- templates or skills

Not every task needs a retrospective. Use one when something learned should improve future work.

### 7. Propagate related changes
Before finishing, check whether related files also need updates, such as:
- canonical documentation
- templates
- agent instructions
- workflow docs
- examples
- references to renamed or newly introduced artifacts

The task is not complete if obvious propagation work is left behind.

### 8. Finalize with a clean commit
For substantial changes, use the `commit` skill or `/commit` workflow to prepare the final commit message.

Commit messages should:
- clearly describe what changed
- explain why when useful
- stay concise and readable
- reference relevant docs, task logs, or retrospectives when appropriate

Do not include AI or tool authorship boilerplate in the commit title or body unless explicitly requested.

Do not add lines such as:
- `Written by LLM`
- `Generated by AI`
- `Produced with Claude`
- `Co-authored-by Copilot`

## Completion Criteria

A substantial task is complete only when:
- the implementation is done
- relevant canonical documentation is updated if durable truth changed
- a task log exists if the repository uses task logs and meaningful task history would otherwise be lost
- a retrospective exists if the repository uses retrospectives and meaningful reusable lessons emerged
- obvious propagation updates are complete
- the final commit message follows repository standards

## Working Rules

When in doubt:
1. update canonical documentation if durable system truth changed
2. add a task log if the repository uses task logs and meaningful implementation history would otherwise be lost
3. add a retrospective if the repository uses retrospectives and the task revealed lessons that should improve future work
4. use `commit` or `/commit` for substantial changes
5. keep commit messages free of AI/tool authorship boilerplate unless explicitly requested

## Suggested Invocation Pattern

Typical usage:

- use `research-codebase` if repository context is unclear
- use `create-plan` for substantial or ambiguous work
- use `implement-plan` to carry out the plan
- use `commit` to prepare the final commit message

## Output Expectations

When using this skill, the agent should usually make clear:
- what it believes the task is
- what files it expects to change
- whether canonical documentation will need updates
- whether a task log is warranted
- whether a retrospective is warranted

Before finishing, the agent should summarize:
- what changed
- which docs were updated
- whether a task log was added or updated
- whether a retrospective was added or updated
- how the final commit was prepared
