# Commit Messages

This project uses commit messages to preserve clear human-readable history about what changed and why.

## Goals

A good commit message should help a future maintainer quickly understand:

- what changed
- why it changed
- whether relevant docs were updated
- where to find deeper task history or lessons when needed

## When to Use the `/commit` Skill

If your project uses the `/commit` skill, use it for substantial changes. Otherwise write the commit message manually following this guide.

Examples of substantial changes:
- changes that affect multiple files
- behavior changes
- architecture or design changes
- changes that update canonical docs
- changes that introduce or update task logs or retrospectives
- changes that would benefit from a clear explanation of why they were made

For very small or routine changes, a short manual commit message is fine.

## Commit Message Style

Prefer:

- a short, clear title in imperative mood
- a concise body when additional context is useful
- plain English
- wording that describes the change and its rationale

Avoid:

- vague titles
- unnecessary jargon
- overly long bodies
- process noise that does not help explain the change

## Title Template

Use a short imperative title that describes the outcome.

Examples:
- `Add task log guidance to docs`
- `Clarify debugger session lifecycle`
- `Document retrospective workflow for substantial tasks`

## Body Template

When a body is useful, prefer this structure:

### Why
Why was this change needed?

### What changed
What was added, removed, or clarified?

### Docs updated
Which canonical docs were updated?

### Task history
If relevant, link or refer to:
- task log
- retrospective

Example:

```text
Why
- Squash merges can hide important implementation history.
- We want durable process memory for agent-driven work.

What changed
- Added task log guidance to docs/README.md.
- Added retrospective guidance and templates.
- Added CLAUDE.md guidance for agent expectations.

Docs updated
- docs/README.md
- docs/retrospectives/TEMPLATE.md
- CLAUDE.md

Task history
- Task log: docs/task-logs/...
- Retrospective: docs/retrospectives/...
```

Not every commit needs all sections. Use the sections that improve clarity.

## AI and Tool Authorship Policy

Do not include AI-authorship or tool-authorship boilerplate in commit titles or bodies unless explicitly requested.

Do not add lines such as:
- `Written by LLM`
- `Generated by AI`
- `Produced with Claude`
- `Co-authored-by Copilot`

The commit history should focus on the change and its rationale, not on which tool drafted the message.

## Relationship to Other Artifacts

Use commit messages for a concise summary of the change.

Use other artifacts for deeper context:
- `docs/` for canonical system truth
- `docs/task-logs/` for meaningful task execution history
- `docs/retrospectives/` for lessons that should improve future work

A commit message does not need to capture the full conversation or every iteration. If that history matters, record it in a task log.

## Working Rule

When in doubt:
- use `/commit` for substantial changes
- keep the message concise and specific
- include the why when it helps
- reference docs, task logs, or retrospectives when relevant
- do not include AI authorship boilerplate
